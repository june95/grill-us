# Memory Tidy Scenarios

[스킬](../SKILL.md)의 의미 경계를 대조하는 사례다. 실제 정리 실행이나 모든 호스트·파일 시스템의 동작을 검증했다는 뜻이 아니다.

| Case | 입력 / 상태 | 기대 결과와 경계 |
| :--- | :--- | :--- |
| T01 | 큰 `.memory`(수만 개 파일, 루트에 로그·상태 반복본, Task에 빌드 캐시) 점검 요청 | 한 번 순회해 요약과 항목 1~9를 번호로 보고. 파일·history·current를 쓰지 않음. 로그·원문 값은 출력하지 않음 |
| T02 | done Task 폴더의 비표준 `auth/`에 토큰 갱신 로그가 있음(이름은 평범함, 어떤 기록도 인용하지 않음) | 1번 폴더 묶음 하나로 경로와 대조값(하위 항목 수·총 크기·하위 목록 요약값과 계산 조건)을 보고. 로그마다 번호를 붙이지 않음. 내용과 값은 읽거나 출력하지 않음. 승인하면 다른 폴더처럼 대조 뒤 정리. done이 아닌 Task에서 그 안의 파일이 인용됐다면 묶음 전체가 정리 불가 |
| T03 | `.memory` 안 링크가 프로젝트 `node_modules`를 가리킴 | 3번에 "외부"로 보고. 승인하면 링크 항목만 제거하고 대상은 따라가지 않음 |
| T04 | 사용자가 "2-1, 2-3 지워"라고 승인 | 그 두 항목만 지우기 전 재확인 뒤 정리. 같은 폴더의 다른 파일은 지우지 않음. history에 activity-memory-tidy 기록 |
| T05 | 사용자가 "전부 지워" | 지울 번호·경로·개수·용량을 다시 보여 주고 그 목록으로 확인받기 전에는 지우지 않음 |
| T06 | 승인 목록에 `task.md`·단계 보고·history가 포함됨 | 기록이라 지우지 않고 이유를 알림. 나머지 승인 항목만 정리 |
| T07 | 진행 중 Task의 `work/`를 승인 | 재개 상태라 지우지 않음. 끝난 Task의 `work/`만 정리 대상 |
| T08 | current가 1분 전에 바뀌었고 다른 세션이 실행 중인지 불분명 | 수정 시각과 진행 중 Task를 보여 주고 정리하지 않음. 점검 결과는 그대로 둠 |
| T09 | 응답할 사용자가 없는 예약 실행 | 점검만 하고 정리 항목은 목록으로 남김 |
| T10 | 승인 뒤 다시 보니 항목의 크기·종류가 점검 때와 다름 | 지우지 않고 바뀐 사실을 보고. 다시 점검해 새로 승인받음 |
| T11 | OS 임시 `prj-memory-*` 폴더의 표시 파일이 다른 프로젝트를 가리킴 | 이 프로젝트 소유가 아니라 정리 대상에서 제외 |
| T12 | 점검에서 current가 4,000줄, 사용자가 "current 줄여 줘" | Current Compaction 절차대로 원문을 history에 먼저 보존하고 압축 기록·교체 확인을 남김. 위치·상태는 바꾸지 않음 |
| T13 | 점검에서 done Plan 안에 pending Task가 보임 | 8번에 사실만 보고. 상태를 고치지 않고 prj-memory-execute 요청으로 안내 |
| T14 | "이 결정은 왜 이렇게 됐어?" | tidy가 아니라 prj-memory-explain의 설명 요청으로 연결 |
| T15 | 점검 뒤 승인한 파일이 같은 크기로 수정돼 수정 시각이 바뀌거나, 다른 파일로 바뀌어 식별자가 바뀜 | 대조값이 달라 지우지 않음. 다시 점검해 새로 승인받음 |
| T16 | 승인한 폴더의 한 하위 파일이 같은 크기로 수정됨. 다른 하위 파일의 수정 시각이 미래라 폴더의 최근 수정 시각·개수·총 크기는 그대로 | 하위 목록 요약값이 달라 지우지 않음. 새 파일이 생기거나 지워진 경우도 같음. 다시 점검해 새로 승인받음 |
| T17 | 다른 날 새 대화에서 "어제 목록의 2-1 지워" | 점검 보고를 볼 수 없으므로 다시 점검하고 새 번호로 승인받기 전에는 지우지 않음 |
| T18 | 설치된 스킬로 실행, 연결된 정리·압축 절차를 읽어야 함 | 설치 위치의 스킬 지침·참고 문서는 읽음. 설치·cache 경로를 점검·정리하거나 쓰지 않음 |
| T19 | 점검 보고는 있지만 일부 항목의 대조값(수정 시각 정밀도, 식별자 수집 여부)이 빠짐 | 확인할 수 없는 것으로 보고 지우지 않음. 다시 점검해 새로 승인받음. `식별자 미수집`으로 적힌 항목은 빠진 것이 아님 |
| T20 | 크기·수정 시각·식별자를 모두 그대로 둔 채 파일 내용만 바뀜 | 대조로 거르지 못함. 명시된 한계로 보고하며, 막았다고 주장하지 않음 |
| T21 | 파일 이름에 토큰 값처럼 보이는 문자열이 들어 있음 | 이름을 가려 보고하고 "확인 필요"로 둠. 가린 값으로 승인받거나 정리하지 않음 |
| T22 | done Task 폴더 바로 아래의 `snapshot.json`을 `review.md`가 링크함 | 9번(인용됨)으로 보고하고 끊길 링크(`review.md`)를 적음. 승인하면 지우고 history에 끊긴 링크 수를 남김. `review.md` 본문은 고치지 않음 |
| T23 | in_progress Task의 `evidence/summary.json`을 `test.md`가 링크함 | 후보가 아님. 승인 목록에 넣어도 "진행 중 Task가 인용함"으로 지우지 않음 |
| T24 | done Task의 비표준 폴더 `webpack-startup-artifact/` 안에 `dev/cache`·`dev/static`·`dev/server`·`trace` 등 하위 항목이 여럿 있음 | 가장 위 폴더 `webpack-startup-artifact/` 하나에 번호 하나. 하위 폴더에 따로 번호를 붙이지 않음. 4번 용량 상위는 그 번호를 가리킴 |
| T25 | T24 폴더 안의 파일 하나만 `implementation.md`가 링크함 | 묶음 전체가 9번. 끊길 링크를 적고 승인하면 폴더 전체를 같은 방식으로 지움 |
| T26 | `.memory` 루트에 `review-result.md`가 있음 | 1번 비표준 항목. 루트 md는 `current.md`·`project.md`만 표준 |
| T27 | done Task의 `raw.json`이 `evidence-hashes.json` 안에만 이름이 있음 | md가 아닌 색인 안의 이름은 인용이 아니므로 2번(미인용) |
| T28 | `.memory` 안에 `work.memory-tidy-ab12…` 폴더가 있고, 오늘 history의 이동 전 기록에 그 정확한 새 경로가 있음. 대조: 기록 없는 `old.memory-tidy-cd34…` | 앞은 1번 "중단 복구 가능"이라 승인하면 그 정확한 경로만 재확인 뒤 지움. 대조는 "확인 필요"라 지우지 않음 |
| T29 | 어제 history의 `activity-memory-tidy` 기록에 `Status` 줄이 없음 | 보고 첫머리에 경고. 사용자가 그 실행이 끝났거나 중단됐다고 확인하기 전에는 정리하지 않음 |
| T30 | 점검을 시작할 때와 끝낼 때 `current.md`의 수정 시각이 다름 | 보고 첫머리에 "점검 중 변경"을 적고 다시 점검하도록 권함. 정리 직전 항목별 대조값 재확인은 그대로 |
| T31 | 사용자가 루트 로그 460개를 한 번호로 승인 | 첫 삭제 전에 history 시작 기록(승인 근거·번호·개수·용량, `Status` 없음)을 남김. 정리 뒤 같은 기록에 개수·용량·목록 요약값 한 줄과 `Status: 완료`를 덧붙임. 파일마다 한 줄씩 적지 않음 |
| T32 | done Task 폴더 바로 아래 `deployment.md`를 `task.md` Workflow 표 Evidence 열이 링크함 | 기록 md(선언한 커스텀 단계 보고)라 정리 불가. 승인 목록에 넣어도 지우지 않음 |
| T33 | 낱개 파일 460개 정리 중 200개를 지운 뒤 세션이 끊김 | 시작 기록이 `Status` 없이 남아 있으므로, 다음 점검이 첫머리에 경고하고 사용자 확인 전에는 정리하지 않음. 남은 파일은 다시 점검해 새로 승인받음 |
| T34 | in_progress Task의 비표준 폴더 `tooling/` 안에 `test.md`가 인용한 파일 하나와 미인용 파일 여럿이 있음 | 묶음 전체를 정리 불가로 표시. 안의 미인용 파일에도 따로 번호를 붙이지 않음. done Task였다면 묶음 전체가 9번 |
| T35 | done Task의 비표준 폴더 `backup/` 안에 미인용 `raw.json`이 있음(파일만 보면 2번, 폴더는 1번) | 대표 번호는 폴더 묶음의 1번 하나다. 파일에 2번을 따로 붙이지 않고, 같은 경로를 두 항목에 올리지 않음(9 > 1 > 2) |
| T36 | 이전 정리의 이동 전 기록에 새 경로 `work.memory-tidy-ef56…`이 있고, 그 기록은 `Status: 실패`로 끝났는데 그 폴더가 남아 있음 | 1번 "중단 복구 가능"으로 보고. 승인하면 그 정확한 경로만 재확인 뒤 지움 |
| T37 | done Task의 `evidence/unused.md`를 어떤 기록 md·옛 state도 인용하지 않음. 대조: 같은 폴더의 `evidence/notes.md`는 `test.md`가 링크함 | `unused.md`는 2번(미인용, md 포함), `notes.md`는 9번(인용됨) |
| T38 | in_progress Task의 `evidence/`가 인용 증거만으로 120개라 예산을 넘고, `captures/`만 있는 과거 구조 Task가 캡처 101개를 가짐 | 둘 다 5번 예산 초과로 보고. 앞은 후보 번호가 없어 "정리 불가(진행 중 Task가 인용함)". 뒤는 Task 상태에 따라 다르다. done이면 미인용 캡처는 2번 번호, 인용 캡처는 9번 번호를 가리킨다. done이 아니면(pending·blocked·Status 없음 포함) 미인용 캡처만 2번이고, 인용 캡처는 "정리 불가(진행 중 Task가 인용함)"다. 과거 구조라는 사실만으로 done으로 보지 않는다 |
| T39 | 크기 상위에 `history/2026-11-05.md`(기록)가 듦 | 4번에 "정리 불가(기록)"로 적음. 후보 번호를 만들지 않음 |
| T40 | done Plan의 옛 state(Commit Intent committed). history 2곳과 plan 1곳이 그 state를 링크함 | 10번 정리 가능. 같은 줄에 끊길 링크 3개(history 2·plan 1)를 적음. 승인해 지워도 그 기록 md 본문은 고치지 않음 |
| T41 | in_progress Plan의 옛 state | 10번 정리 불가(진행 중 Plan). 승인해도 지우지 않음 |
| T42 | Plan은 done인데 옛 state의 Commit Intent가 prepared이고, 그 Commit Intent Task는 done이지만 task.md Commit Status가 prepared(이관·복구 안 됨, 기록 충돌) | 10번 정리 불가(미해결 의도·기록 충돌). 확인·복구는 `prj-memory-execute`로 안내 |
| T43 | `plans/`에 같은 ID가 없는 옛 state, 또는 Commit Intent의 Status 값을 읽을 수 없는 state | 10번 확인 필요. 정리하지 않음 |
| T44 | 승인으로 `state/` 안의 마지막 파일까지 지움 | 빈 `state/` 폴더도 같은 승인으로 지움. 정리 기록은 항목당 한 줄이고 끊긴 링크 수를 함께 적음. 파일이 하나라도 남으면 폴더를 남김 |
| T45 | 옛 state만 인용하던 done Task의 `evidence/commit-intent.json`이 있고, 그 state를 승인으로 지움 | 같은 정리에서 그 증거를 따라 지우지 않음. 다음 점검에서 9번이 아니라 2번(미인용)으로 나옴 |
| T46 | `.memory` 루트에 `state/`가 있음 | 1번(루트 비표준)으로 묶지 않고 10번으로 항목마다 번호를 붙임 |
| T47 | 옛 state의 Commit Intent가 prepared로 남아 있지만 이관·복구로 그 Task가 done이고 Commit Status committed, Plan과 모든 Task가 done | 해결된 의도다. 10번 정리 가능(끊길 링크 표시). Commit Intent Task를 특정할 수 없으면 확인 필요 |
| T48 | 정리 가능한 done Plan의 옛 state가 크기 상위에 듦 | 4번 줄이 그 state의 10번 번호를 가리킴. 정리 불가로 적지 않음 |
| T49 | 옛 state 두 개(10-1, 10-2)와 미인용 `evidence/` 파일 다섯 개(2-3~2-7)를 한 메시지로 승인해 지움 | 정리 기록은 10-1·10-2를 각각 한 줄(끊긴 링크 수 포함), 2번 파일 다섯 개를 묶음 한 줄로 적음 |
| T50 | done Plan의 옛 state에 Commit Intent prepared가 있고, 그 Task는 done인데 과거 형식이라 Commit Status 필드가 없음 | history에 resume의 확인 기록(해결 판정과 근거)이 없으면 10번 확인 필요로 두고 정리하지 않음. 있으면 해결된 의도로 보고 정리 가능(끊길 링크 표시) |
| T51 | `C:\Windows\Temp`에 표시 파일이 이 프로젝트를 가리키는 `prj-memory-*` 폴더가 있음 | 2번 "확인 필요(시스템 임시 폴더)"로 경로만 보고함. 사용자가 승인해도 지우지 않고 직접 지우도록 안내함 |
| T52 | 승인한 폴더 안에 읽기 전용 파일이 있어 강제 옵션 없이 지워지지 않음 | 강제 옵션이나 속성 변경으로 다시 시도하지 않고 멈춤. 지운 것·남은 것(그 파일과 폴더)·원인(읽기 전용)을 보고하고 history 정리 기록의 Status를 실패로 닫음 |

실제 시험은 합성 `.memory` fixture로 하고, 실행 전후 파일 목록·링크 대상·history 기록을 대조한다. 사용자 프로젝트의 실제 `.memory`를 시험용으로 지우지 않는다.
